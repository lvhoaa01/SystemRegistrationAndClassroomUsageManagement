Mình đề xuất nhóm dùng một bộ **Git Commit & Push Rules** đủ chặt để tránh conflict nhưng không quá rườm rà. Có thể gửi nguyên văn cho thành viên như sau:

## Quy tắc Commit & Push của nhóm

1. **Không commit trực tiếp lên `main`.** Mỗi người làm trên branch riêng theo task/module, ví dụ:
   ```text
   feat/search-allocation
   feat/property-management
   feat/inventory-calendar
   fix/booking-concurrency
   ```

2. **Mỗi commit phải là một đơn vị công việc logic hoàn chỉnh — Atomic Commit.** Không commit theo từng file hoặc từng vài dòng code. Một commit nên trả lời được câu hỏi: *“Commit này hoàn thành việc gì?”*  
   Ví dụ tốt:
   ```text
   feat(properties): add property creation and validation
   feat(search): implement room-product allocation
   fix(bookings): prevent inventory overselling
   ```
   Không nên:
   ```text
   update file
   fix code
   modify
   test
   update again
   ```

3. **Không gom nhiều việc không liên quan vào cùng một commit.** Ví dụ sửa đăng nhập và thêm thuật toán xếp phòng phải thành hai commit:
   ```text
   fix(identity): validate locked user before login

   feat(search): implement multi-room allocation
   ```

4. **Commit chỉ khi phần việc đang ở trạng thái hợp lệ.** Trước commit cần kiểm tra tối thiểu:
   ```text
   code chạy được
   không có syntax error
   chức năng vừa làm test được
   không làm hỏng chức năng cũ liên quan
   không để debug code như var_dump(), print_r(), console.log()
   ```
   Nếu đang làm dở và bắt buộc phải lưu thì dùng branch cá nhân, không merge phần đó vào `main`.

5. **Trước khi push phải cập nhật code mới nhất từ remote.**
   ```bash
   git fetch origin
   git pull --rebase origin main
   ```
   Nếu branch đang làm lâu, nên cập nhật `main` thường xuyên để tránh dồn conflict đến cuối.

6. **Không force push lên branch dùng chung hoặc `main`.**
   ```bash
   git push --force
   ```
   chỉ được dùng trên branch cá nhân khi người thực hiện hiểu rõ hậu quả. Tuyệt đối không dùng để “xóa conflict cho nhanh”.

7. **Không push dữ liệu nhạy cảm hoặc file không thuộc source code.** Không commit:
   ```text
   .env
   password
   API key
   database credential
   file log
   file tạm
   vendor/ nếu dùng dependency manager
   dữ liệu cá nhân
   ```
   Các file cấu hình mẫu dùng:
   ```text
   .env.example
   ```

8. **Mỗi task nên có chuỗi commit dễ đọc từ đầu đến cuối.** Ví dụ một người làm module booking:
   ```text
   feat(bookings): add booking repository

   feat(bookings): validate booking preview

   feat(bookings): add booking transaction

   feat(inventory): add nightly inventory ledger

   test(bookings): add last-unit concurrency test

   fix(bookings): make booking retry idempotent
   ```
   Nhìn Git history là biết người đó đã làm gì, thay vì một commit khổng lồ:
   ```text
   feat: complete reservation module
   ```

### Quy ước commit message

Mình khuyên dùng dạng:

```text
<type>(<scope>): <mô tả ngắn>
```

Các `type` chính:

```text
feat      thêm chức năng
fix       sửa lỗi
refactor  tái cấu trúc, không đổi behavior
test      thêm/sửa test
docs      tài liệu
style     format code, CSS, UI không đổi logic
chore     config, dependency, tooling
db        thay đổi schema/seed/database
```

Ví dụ cho project này:

```text
feat(properties): add property facility management
feat(pricing): add daily rate calendar
feat(search): implement available product filtering
feat(search): implement multi-room allocation
feat(bookings): create booking from preview
fix(inventory): prevent last-unit overselling
db(bookings): add client request unique constraint
refactor(inventory): extract availability service
docs: update cancellation workflow
```

### Workflow chuẩn cho mỗi task

```text
Nhận task
   ↓
Tạo / chuyển sang branch
   ↓
Code một đơn vị logic
   ↓
Test
   ↓
git add
   ↓
Atomic commit
   ↓
Tiếp tục task nếu còn
   ↓
Cập nhật main mới nhất
   ↓
Resolve conflict nếu có
   ↓
Test lại
   ↓
Push branch
   ↓
Merge / Pull Request
```

Ví dụ cụ thể:

```bash
git checkout main
git pull origin main

git checkout -b feat/search-allocation

# code...

git add .
git commit -m "feat(search): implement available product filtering"

# code tiếp...

git add .
git commit -m "feat(search): implement multi-room allocation"

git fetch origin
git rebase origin/main

# test lại

git push -u origin feat/search-allocation
```

Một nguyên tắc mình muốn nhấn mạnh với nhóm là:

> **Không đo năng suất bằng số commit. Commit phải đại diện cho một thay đổi logic có ý nghĩa, đủ nhỏ để review và đủ hoàn chỉnh để có thể hiểu hoặc revert độc lập.**

Cách này đặc biệt hợp với cấu trúc **module theo feature** mà nhóm mình đang định dùng, vì mỗi thành viên có thể phụ trách một module và Git history cũng phản ánh đúng ranh giới công việc.
